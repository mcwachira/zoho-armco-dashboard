# Operational dashboard API contract

This document is the middleware contract for the separately deployed dashboard gateway. The gateway calls this API; it must not connect to PostgreSQL, Zoho Books, the G03 device, or ZFPLabServer directly.

## Authentication and common rules

All `/api/dashboard` routes require the existing dashboard session and `dashboard:read` permission, or the configured gateway service bearer for GET requests only. The service bearer never authorizes mutations. Responses use JSON. Errors use `{ "error": { "code": string, "message": string } }`. Internal stack traces, credentials, authorization headers, and customer tax identifiers are not response fields.

List routes use `page` (1-based, default 1) and `pageSize` (default 25, maximum 100 unless noted). New manual-review, reconciliation, event, and pending-operation lists cap `page` at 100; document and fiscalization-history routes retain their route-specific limits. Paginated persistence responses are `{ page, pageSize, total, items }`. Live Zoho Books register responses are `{ page, pageSize, total: null, hasMore, items }`; Zoho Books does not provide a reliable total for the client methods used here. Invalid query values return 400; missing records return 404; unavailable dependencies return 503; failed Zoho upstream reads return 502. Dates are ISO-8601 UTC strings.

Document detail fields returned from Zoho retain Zoho's document representation. Register rows include a nullable `fiscalizationRequest` projection with request ID, persisted status, receipt fields, and attempt count. Treat `fiscalizationRequest: null` as "not processed by this middleware", not as a failed request. Zoho status and middleware fiscalization status are independent. Fiscalization and transmission state are exposed as joined values, but Zoho's upstream list API cannot filter on middleware-only state; apply those filters in the dashboard over fetched pages or persisted history.

## Operations

The authenticated dashboard action routes require a Better Auth session and `dashboard:operate`. Viewer accounts cannot mutate. The configured service bearer remains GET-only. These routes delegate to established Zoho button, fiscalization workflow, and writeback services. The dashboard must not construct fiscalization payloads.

| Method and path                                                                         | Access                                   | Response and idempotency                                                                                                                                                                                                                                                                                                                                                                                  |
| --------------------------------------------------------------------------------------- | ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /api/dashboard/actions/fiscalize`                                                 | operate                                  | Body fields: `org_id`, `document_type` (`INVOICE` or `CREDIT_NOTE`), `document_id`, `source` (`ZOHO_BOOKS_BUTTON`). Calls the same Zoho button handler, preflight, and orchestration. A newly claimed execution returns HTTP 202 with `status: SUBMITTED`, `already_submitted: false`, and a claim message; an active claim reports processing. If Zoho has both completion fields, execution is skipped. |
| `POST /api/dashboard/actions/invoices/{requestId}/writeback`                            | operate                                  | Empty body. Reuses confirmed persisted invoice fiscal evidence and does not invoke fiscalization.                                                                                                                                                                                                                                                                                                         |
| `POST /api/dashboard/actions/credit-notes/{requestId}/writeback`                        | operate                                  | Empty body. Requires previously persisted authoritative fiscalization evidence and does not invoke G03 or EJ.                                                                                                                                                                                                                                                                                             |
| `POST /integrations/zoho/button-submissions`                                            | existing Zoho button operation           | Same payload validation and fiscalization orchestration as the dashboard action; its existing response value (`status: accepted`) is preserved for Zoho Books compatibility.                                                                                                                                                                                                                              |

Mutation errors use the common error envelope. Expected domain states retain the existing operation status and HTTP mapping. A writeback attempt updates the already identified Zoho document, persists provider exchange evidence, and reports success only after configured-field readback verification.

The middleware has no durable generic event table or unified queue. `/events` is a read model over persisted operational evidence and does not represent every process log or every intermediate status change. `/operations` joins persisted workflow states; it does not provide a single queue depth or a separate worker queue. `/capabilities` reports queue depth as unavailable. Historical uptime is unsupported because process metrics reset at restart. `/writebacks` reads persisted operations; invoice rows expose the durable operation retry count while credit-note rows expose the count of provider exchanges because their persistence models record attempts differently. Manual-review and reconciliation records are exposed directly from their current persistence models; no resolution mutation is exposed through the dashboard API.

## Supported statuses and security

Invoice fiscalization status is one of `Pending`, `InProgress`, `Succeeded`, `Failed`, or `OutcomeUnknown`. Credit-note status is the persisted workflow state. Transmission, reconciliation, and writeback statuses remain separate fields. Receipt numbers and QR URLs are present only when persisted evidence passes the domain's authoritative evidence checks. Never infer a successful receipt from an attempt count or old request alone.

Inputs are strictly validated and bounded. The dashboard namespace never exposes database credentials, provider authorization, request headers, secrets, customer KRA PINs, or full provider exchange payloads. Mutation operations do not issue device commands except through the existing fiscalization orchestration action; writeback actions never invoke the device or fiscalization service.
