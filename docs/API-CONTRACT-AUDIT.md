# Dashboard API contract audit

## Evidence and scope

The middleware source was inspected locally and read-only. Evidence includes `src/routes/dashboard-data-routes.ts`, its route schemas and normalization logic, `src/app.ts` route mounting and authorization middleware, `docs/openapi.yaml`, and `tests/unit/dashboard-data-routes.test.ts` plus `tests/unit/dashboard-app-security.test.ts` in the local middleware source repository. No runtime endpoint was called. No environment secret values were read. The deployed middleware, public gateway, Windows services, database and Zoho submission path were not changed.

The dashboard schemas in `src/features/api/schemas.ts` are the proposed stable frontend DTOs. They are not proof of a separate testing API. The source comparison below reports what the middleware currently implements; the dashboard gateway must only call a separately verified test deployment that explicitly implements the stable contract.

The OpenAPI paths and route registration match for all listed GET routes. Source authorization mounts dashboard routes behind a dashboard session requirement and `dashboard:read`; disabled/missing auth or data configuration returns 503. CORS is exact-origin and credentialed from configured dashboard origins, with GET/OPTIONS. Invalid requests return 400; protected reads return 401/403; missing records return 404; unavailable dependencies return 503. Unknown GETs return 404 and non-GET dashboard methods are rejected.

## Safe-use classifications

- **MATCH:** capabilities, invoice page/detail, credit-note page/detail, overview, writebacks, manual review, reconciliation route method and response intent.
- **MISMATCH:** device and service response shapes versus the dashboard's stricter DTOs described above. A future adapter must normalize only verified values and preserve unknown/unavailable states.
- **MISSING capability:** complete writeback collection, complete reconciliation records, durable event feed, queue depth, historical uptime, device fleet identity/history, manual-review total, financial aggregates and processing-time trends.
- **UNKNOWN:** whether any independently hosted testing API exists, its host, authentication, route allowlist, network reachability, or whether it is isolated from production fiscalization. No such testing API was documented in the reviewed dashboard or middleware docs/config examples.
- **NOT_SAFE for dashboard use:** `POST /integrations/zoho/button-submissions`, Zoho writeback POSTs, fiscalization execute/process/retry/replay routes, manual-review decision routes, reconciliation mutation/retry routes, credit-note submission/execute routes, and device diagnostic/probe/control routes. These can mutate business or fiscalization state. Raw integration GETs are also not a substitute for the dedicated sanitized dashboard contract.

The existing `POST /integrations/zoho/button-submissions` remains the separate working Zoho workflow and must not be used or changed by dashboard integration.

## Testing API decision

No independent dashboard testing API was found. The `g11server.tailaff2e5.ts.net` hostname is documented in project context as the existing Zoho gateway/Funnel path, not as a dashboard test service. The local middleware source is not an independent testing API. Therefore this repository does not activate an upstream. The dashboard gateway fails with an explicit `UPSTREAM_UNCONFIGURED` state until a separate HTTPS test service is independently documented and approved. It never falls back to fixtures in API mode.

Vercel has no verified tailnet connection in this repository. A tailnet-only test API is not assumed reachable from Vercel Functions. Before configuring a test upstream, confirm its network access path, host, read-only route allowlist, auth and response contract without involving production fiscalization.
